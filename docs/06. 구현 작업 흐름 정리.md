작성일: 2026-05-23

이 문서는 `docs/05. 통신 API 설계.xlsx`와 `docs/03. ERD.drawio`를 참고하여 이번 피드에서 진행한 컨트롤러 및 서비스 구현 흐름을 순서대로 정리한 것이다.

## 1. API 설계 문서 확인

- 로그인, 로그아웃, 회원가입, 토큰 갱신, 내 정보 조회/수정/탈퇴

엑셀 파일은 `openpyxl`이 없는 환경이었기 때문에 `.xlsx` 내부 XML을 Python 표준 라이브러리(`zipfile`, `xml.etree.ElementTree`)로 직접 읽어 필요한 행을 추출했다.

## 2. 기존 컨트롤러 구조 파악

`VmsDeviceController`를 기준 포맷으로 삼아 현재 프로젝트의 컨트롤러 작성 방식을 확인했다.

확인한 패턴은 다음과 같다.

- 각 handler 함수 안에서 `httpServer.addRoute(...)` 호출
- 요청 파라미터는 `req.getPathParam(...)`, `req.getQueryParam(...)` 사용
- JSON 응답은 `nlohmann::json`으로 구성
- 응답은 `Http::Response`에 status, header, body를 직접 설정하거나 `VmsApiResponse` 헬퍼 사용

이후 구현에서는 가능한 한 이 형식을 유지했다.

## 3. VmsPlaybackController 구현

대상 파일:

- `include/vms-api/VmsPlaybackController.h`

헤더에는 이미 필요한 함수 선언이 존재했으므로 `VmsPlaybackController.cpp`의 빈 handler를 채웠다.

구현한 라우트는 다음과 같다.

- `GET /devices/{deviceId}/playback/segments`
- `GET /devices/{deviceId}/playback/timeline`
- `GET /devices/{deviceId}/playback/stream`
- `GET /devices/{deviceId}/playback/download`
- `GET /playbacks/{segmentId}`
- `GET /playbacks/{segmentId}/stream`
- `GET /playbacks/{segmentId}/download`
- `GET /playbacks/{segmentId}/thumbnail`

처리 내용:

- 엑셀 문서의 예시 응답을 기준으로 샘플 JSON 응답 작성
- 영상 스트림, 다운로드, 썸네일 API는 실제 바이너리 파일 전송 대신 placeholder body 반환
- `Content-Length`는 placeholder body 길이와 문서상의 값이 다르면 클라이언트가 대기할 수 있어 수동 설정하지 않고 서버 직렬화가 자동 설정하도록 정리
- 문서에 있는 `hight` 오타와 일반적인 `height` 쿼리 파라미터를 둘 다 허용
- 라우트 등록은 컨트롤러 생성 시 활성화되도록 생성자에서 호출

검증:

- `g++ -std=c++17 -fsyntax-only`로 `VmsPlaybackController.cpp` 단독 문법 검사 통과

## 13. 2026-06-10 ONVIF provisioning 흐름 정리

오늘 진행한 작업은 ONVIF 장비 검색 이후 실제 장비 정보를 수집하고 DB 저장 흐름까지 연결하기 위한 기반 작업이다.

전체 흐름은 다음 순서로 정리했다.

```text
WS-Discovery
  -> Device.GetDeviceInformation
  -> Device.GetCapabilities
  -> Media.GetProfiles
  -> Media.GetStreamUri
  -> ProvisioningResult 생성
  -> OnvifProvisioningRepository 저장
```

이 흐름에서 `Discovery`는 장비의 Device Service URL 후보를 찾고, `GetCapabilities`는 Media Service endpoint인 `mediaXAddr`를 확보한다. 이후 `GetProfiles`로 profile token을 얻고, `GetStreamUri`로 media-server가 사용할 수 있는 RTSP/RTP URI를 확보한다.

```cpp
OnvifMediaClient::getStreamUri(mediaXAddr, profileToken);
```

`GetStreamUri`의 기본 요청은 라이브 RTSP 수신에 맞춰 `RTP-Unicast over RTSP`로 둔다.

## 15. onvif-manager 구성

대상 파일:

- `include/onvif-manager/OnvifDeviceProvisioningService.h`
- `src/onvif-manager/OnvifDeviceProvisioningService.cpp`
- `include/onvif-manager/OnvifProvisioningTypes.h`
- `include/onvif-manager/OnvifProvisioningRepository.h`
- `src/onvif-manager/OnvifProvisioningRepository.cpp`

`ProvisioningResult`는 장비 1대에 대한 ONVIF 수집 결과 DTO로 정의했다.

주요 포함 정보:

- Discovery 원본 정보
- Device Service URL
- Media Service URL
- DeviceInformation
- Capabilities
- Media profiles
- Profile별 Stream URI

현재 `OnvifDeviceProvisioningService`는 discovery snapshot을 읽고, 장비별 ONVIF 호출 작업을 `ThreadPool`에 제출하는 방향으로 작성 중이다. 장비 하나 안에서는 `GetDeviceInformation -> GetCapabilities -> GetProfiles -> GetStreamUri` 순서가 의존 관계를 가지므로 순차 수행하고, 장비 간 병렬화를 `ThreadPool`로 처리하는 구조가 적절하다.

주의할 점:

- worker lambda에서 `device`는 reference가 아니라 value로 capture해야 한다.
- provisioning loop는 future를 모아서 한 사이클의 결과를 수집한 뒤 repository에 전달해야 한다.
- loop가 너무 빠르게 돌며 같은 장비 작업을 무한히 enqueue하지 않도록 sleep, interval, sync-in-progress 관리가 필요하다.
- `stop()`에서는 `running = false`, thread join, discovery stop 순서를 안전하게 정리해야 한다.

## 16. ONVIF DB 저장 흐름

ERD 기준으로 ONVIF provisioning 결과는 우선 다음 테이블에 저장하도록 잡았다.

- `devices`
- `device_health`
- `channels`
- `profiles`

추가한 mapper:

- `resources/db/onvif.yml`

현재 repository는 다음 순서로 저장한다.

```text
ProvisioningResult
  -> devices select/insert/update
  -> device_health upsert
  -> channels select/insert/update
  -> profiles select/insert/update
```

`devices`는 `endpointReference`를 `uuid`에 매핑한다. `channels`는 현재 장비당 기본 `channel_no = 1`로 저장한다. `profiles`는 `onvif_profile_token`과 `cctv_rtsp_url`을 저장한다.

현재 구현은 기능 연결과 초기 테스트를 위한 1차 형태다. 실제 운영 규모를 고려하면 DB round-trip을 줄이기 위한 bulk 처리 개선이 필요하다.

## 18. app-util 사용법 문서화

대상 파일:

- `lib/app-util/README.md`

정리한 내용:

- `IntervalTimer` 사용법
- `SchedulePolicy::FixedRate`, `FixedDelay`, `SkipMissed` 차이
- `ThreadPool::submit()` future 반환 방식
- `ThreadPool::submit_with_timeout()` 사용법
- `ShutdownMode::Graceful`, `Immediate` 차이
- `IntervalTimer`와 `ThreadPool`을 함께 쓰는 패턴

`ThreadPool`은 `std::packaged_task`와 `std::future` 기반으로 작업 결과를 반환할 수 있다. 따라서 ONVIF provisioning 작업처럼 `std::optional<ProvisioningResult>`를 반환하는 작업에도 사용할 수 있다.

## 19. DB bulk 처리 개선 필요

현재 `OnvifProvisioningRepository::upsert()`는 `std::vector<ProvisioningResult>`를 받지만 내부에서는 장비별로 반복하면서 단건 SQL을 여러 번 호출한다.

현재 방식의 장점:

- 현재 `AppDb` API로 바로 구현 가능
- 실패한 row 추적이 쉽다
- 실제 DB unique constraint가 아직 확정되지 않아도 동작 흐름을 확인할 수 있다
- 초기 테스트에 적합하다

현재 방식의 한계:

- 장비 수가 많아질수록 DB round-trip이 크게 증가한다
- 여러 statement가 하나의 transaction으로 묶이지 않는다
- 중간 실패 시 부분 저장 상태가 생길 수 있다
- 대량 provisioning에는 비효율적이다

따라서 실제 카메라 몇 대로 저장 흐름을 검증한 뒤 `app-db` 자체를 transaction/bulk 처리 가능하게 업그레이드해야 한다.

필요한 DB constraint 후보:

```text
devices.uuid UNIQUE
channels(device_id, channel_no) UNIQUE
profiles(channel_id, onvif_profile_token) UNIQUE
device_health.device_id PRIMARY KEY 또는 UNIQUE
```

필요한 `app-db` 개선 후보:

- 명시적 transaction API
- batch executor
- JSONB parameter 기반 bulk query 지원
- PostgreSQL `COPY` 또는 `jsonb_to_recordset` 기반 bulk insert/upsert 지원
- mapper에서 bulk statement를 안전하게 표현하는 규칙

장기적으로는 repository를 다음 형태로 개선하는 것이 좋다.

```text
OnvifProvisioningRepository.bulkUpsert(results)
  -> bulk upsert devices
  -> uuid -> device_id mapping 반환
  -> bulk upsert device_health
  -> bulk upsert channels
  -> channel mapping 반환
  -> bulk upsert profiles
  -> 하나의 transaction으로 commit
```

PostgreSQL에서는 `jsonb_to_recordset` 기반 bulk upsert가 후보가 될 수 있다.

```sql
INSERT INTO devices (...)
SELECT ...
FROM jsonb_to_recordset($1::jsonb) AS x(...)
ON CONFLICT (uuid) DO UPDATE SET ...
RETURNING device_id, uuid;
```

이 방식으로 가려면 C++ 쪽에서 `ProvisioningResult` 목록을 JSON 배열로 직렬화하고, mapper에는 JSONB parameter 하나를 넘기는 형태가 필요하다.
