표시는 다음과 같은 의미를 가진다.
- `[x]`는 해당 코드/설정의 구현 또는 기존 작업 기록
- `[~]`는 일부 구현
- `[ ]`는 남은 구현·검증 작업

과거 문법 검사와 빌드·패키징 실행 결과는 19절 및 날짜별 과거 기록으로 분리한다.

현재 코드에서 연결된 흐름은 `ONVIF discovery → Device/Media 조회 → 장비·채널·profile DB 저장 → H.264 ingest → MP4 녹화 및 공유 RTSP relay → archive_segment DB 저장 → 목록·타임라인·HLS VOD API`다. 

사용자·관리자·장비·재생 컨트롤러와 공통 인증 middleware는 `VmsApplication`에 연결되어 있다. 이벤트 컨트롤러는 샘플 구현이며 runtime에는 연결되지 않았다.

## 11. ONVIF provisioning 흐름 정리

기준 흐름:

```text
WS-Discovery
  -> Device.GetDeviceInformation
  -> Device.GetCapabilities
  -> Media.GetProfiles
  -> Media.GetStreamUri
  -> ProvisioningResult 생성
  -> MediaService.addCamera(results)
  -> OnvifProvisioningRepository.ensureChannel / upsertProfiles
  -> profile_id 조회 및 relay mount 등록
  -> CameraManager.add_camera(CameraConfig)
  -> GStreamer ingest/recording 및 H264RelayHub 기반 relay
  -> archive_segment DB 저장 / Playback API
```

완료:

- [x] Discovery 이후 실제 장비 정보 수집 흐름 정리
- [x] `Discovery`에서 Device Service URL 후보 확보
- [x] `GetCapabilities`에서 Media Service endpoint인 `mediaXAddr` 확보
- [x] `GetProfiles`에서 profile token 확보
- [x] `GetStreamUri`에서 media-server가 사용할 RTSP/RTP URI 확보
- [x] `ProvisioningResult` 생성 흐름 정리
- [x] `OnvifProvisioningRepository` 저장 흐름 정리
- [x] `MediaService`에서 `ProvisioningResult`를 `CameraConfig`로 변환하는 흐름 구현
- [x] `GetStreamUri` 결과 RTSP URL을 `CameraManager::add_camera()`로 연결
- [x] ONVIF profile별 stream을 runtime ingest 대상으로 등록하는 1차 흐름 구현
- [x] `GetCapabilities`의 `ptzXAddr`와 Media endpoint를 DB에 저장하고 PTZ/API 조회에 활용

라이브러리에는 WS-Security 설정이 있으나 현재 provisioning worker는 기본 생성한 Device/Media client를 사용한다. 기본 WS-Security는 비활성화되어 있으므로 장비별 인증정보를 provisioning SOAP 호출에 주입하는 연결은 남아 있다. RTSP 수신 인증 옵션도 별도 후속 작업이다.
