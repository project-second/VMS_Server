# ONVIF gSOAP 개발 정리

이 문서는 VMS 서버에서 ONVIF 기능을 직접 XML 하드코딩으로 구현하지 않고, gSOAP 코드 생성과 gSOAP plugin을 이용해 개발하는 흐름을 정리한다.

현재 구현된 범위는 다음과 같다.

- WS-Discovery active Probe
- WS-Discovery passive listener: Hello, Bye 수신
- WS-Discovery Resolve 요청/응답 처리
- ONVIF Device Service `GetDeviceInformation` client wrapper
- ONVIF Device Service `GetCapabilities` client wrapper
- ONVIF Media Service `GetProfiles` client wrapper
- ONVIF Media Service `GetStreamUri` client wrapper
- ONVIF PTZ Service 기본 client wrapper
- ONVIF PTZ Service `GetNodes`, `GetConfigurations`, `GetConfigurationOptions` client wrapper
- WS-Security UsernameToken 인증: PasswordDigest, PasswordText
- `app-security` 공용 `SecretCodec` 기반 plain/raw secret 저장값 처리

아직 Event 서비스와 HTTP Digest 인증은 구현하지 않았다. WS-Security UsernameToken은 Device/Media/PTZ Service client에 적용할 수 있다.

역할은 다음과 같다.

- `lib/app-onvif`: ONVIF 애플리케이션 모듈. Discovery와 Device/Media/PTZ Service 호출을 담당한다.
- `lib/app-onvif/wsdl`: ONVIF에서 제공하는 WSDL/XSD 입력 파일을 둔다.
- `lib/app-onvif/external`: ONVIF WSDL이 참조하는 W3C/OASIS schema를 로컬로 둔다.

초기에 검토했던 `third_party/onvif` 구조는 현재 사용하지 않는다. 생성 코드는 소스 트리에 커밋하지 않고 build directory에 만들며, 수동 작성 코드는 `lib/app-onvif`에 둔다.

## gSOAP를 쓰는 이유

ONVIF는 SOAP 기반 프로토콜이다. SOAP 요청은 단순 JSON이나 REST 호출이 아니라 XML Envelope, Header, Body, namespace, WS-Addressing, WS-Security 같은 규칙을 따른다.

이를 문자열로 직접 만들면 다음 문제가 생긴다.

- XML namespace를 정확히 맞추기 어렵다.
- SOAP Header/Body 구조가 서비스마다 복잡하다.
- 응답 XML parsing 코드가 지저분해진다.
- ONVIF 스펙 변경이나 서비스 확장 시 유지보수가 어렵다.

그래서 gSOAP를 사용한다. gSOAP는 WSDL/XSD 또는 gSOAP import header를 입력으로 받아 C/C++ 타입과 SOAP 호출 함수를 생성한다.

즉 직접 하지 않는 일은 다음과 같다.

- SOAP XML 문자열 생성
- XML namespace 처리
- SOAP Envelope/Header/Body 직렬화
- SOAP 응답 XML 파싱
- WS-Addressing Header 처리

대신 우리가 작성하는 코드는 생성된 C/C++ 함수와 struct를 사용하는 형태가 된다.

## gSOAP 도구

주요 도구는 두 가지다.

```bash
wsdl2h
soapcpp2
```

### wsdl2h

`wsdl2h`는 WSDL/XSD를 읽어서 gSOAP용 C/C++ input header를 만든다. 현재는 ONVIF Device Management WSDL, Media WSDL, PTZ WSDL을 한 번에 읽어서 `onvif_services_wsdl.h`를 생성한다.

현재 CMake가 실행하는 흐름은 다음과 같다.

```bash
wsdl2h -c++17 -x \
  -o build/lib/app-onvif/generated/onvif_services_wsdl.h \
  -I /usr/share/gsoap/import \
  -I lib/app-onvif/external \
  -I lib/app-onvif/wsdl/ver10/schema \
  -t /usr/share/gsoap/WS/typemap.dat \
  lib/app-onvif/wsdl/ver10/device/wsdl/devicemgmt.wsdl \
  lib/app-onvif/wsdl/ver10/media/wsdl/media.wsdl \
  lib/app-onvif/wsdl/ver20/ptz/wsdl/ptz.wsdl
```

주요 옵션 의미:

- `-c++17`: C++17 형태의 gSOAP header 생성
- `-x`: XML sample/schema 부가 출력 생략
- `-o`: 생성 header 경로 지정
- `-I`: import/schema 검색 경로 지정
- `-t`: gSOAP typemap 지정

### soapcpp2

`soapcpp2`는 gSOAP input header를 읽어서 실제 C/C++ 코드를 생성한다. 현재 입력 파일은 `lib/app-onvif/onvif_services.h`다.

```cpp
#import "wsdd.h"
#import "wsse.h"
#import "onvif_services_wsdl.h"
```

이 파일은 Discovery용 `wsdd.h`, WS-Security용 `wsse.h`, Device/Media WSDL에서 생성한 `onvif_services_wsdl.h`를 하나의 생성 단위로 묶는다.

현재 CMake가 실행하는 흐름은 다음과 같다.

```bash
soapcpp2 -c++17 -C -x -w \
  -d build/lib/app-onvif/generated \
  -I /usr/share/gsoap/import:build/lib/app-onvif/generated \
  lib/app-onvif/onvif_services.h
```

주요 옵션 의미:

- `-c++17`: C++17 코드 생성
- `-C`: client-side 코드만 생성
- `-x`: sample XML 생성 생략
- `-w`: WSDL/schema 출력 생략
- `-d`: 생성 산출물 디렉터리 지정
- `-I`: gSOAP import header와 직전 단계에서 생성한 header 검색 경로

## 생성 산출물

`soapcpp2`는 보통 다음 파일들을 만든다.

```text
soapH.h
soapStub.h
soapC.cpp
soapClient.cpp
*.nsmap
```

각 파일의 역할은 다음과 같다.

- `soapH.h`: 생성 타입과 함수 선언을 모은 header
- `soapStub.h`: gSOAP가 생성한 struct/type 정의
- `soapC.cpp`: SOAP 직렬화/역직렬화 코드
- `soapClient.cpp`: SOAP client 호출 stub
- `*.nsmap`: XML namespace mapping table

현재는 `build/lib/app-onvif/generated` 아래에 `wsdd.nsmap`, `DeviceBinding.nsmap`, `MediaBinding.nsmap`이 함께 생성된다. 이 namespace map들은 통합 생성 결과의 namespace table을 담고 있으므로, 코드에서는 한 파일만 include해서 `namespaces[]`를 한 번 정의하고 다른 파일에서는 `extern`으로 공유한다.

## 왜 통합 생성으로 묶었나

Discovery, Device Service, Media Service, PTZ Service를 각각 따로 `soapcpp2`로 생성하면 `soapC.cpp` 안의 serializer/deserializer 심볼이 중복될 수 있다. 예를 들어 XML 기본 타입, SOAP Envelope 타입, WS-Addressing 타입이 두 생성물에 동시에 들어가면 link 단계에서 충돌할 수 있다.

그래서 현재는 다음 순서로 통합 생성한다.

```text
devicemgmt.wsdl + media.wsdl + ptz.wsdl
  -> wsdl2h
  -> build/lib/app-onvif/generated/onvif_services_wsdl.h
  -> onvif_services.h에서 wsdd.h, wsse.h, onvif_services_wsdl.h import
  -> soapcpp2
  -> soapH.h, soapC.cpp, soapClient.cpp, *.nsmap
```

이렇게 하면 Discovery, Device, Media, PTZ가 같은 gSOAP runtime type set과 namespace table을 공유한다.

## ONVIF Discovery 원리

ONVIF Discovery는 일반 HTTP API가 아니라 WS-Discovery라는 SOAP 기반 UDP multicast 프로토콜이다.

Active Probe 흐름은 다음과 같다.

1. VMS가 UDP multicast 주소 `239.255.255.250:3702`로 `Probe` 메시지를 보낸다.
2. 같은 네트워크의 ONVIF 카메라들이 Probe를 받는다.
3. 카메라가 `ProbeMatches` 메시지로 응답한다.
4. 응답 안에 `EndpointReference`, `Types`, `Scopes`, `XAddrs`가 들어 있다.
5. VMS는 `XAddrs`에서 카메라의 ONVIF Device Service URL을 얻는다.

Passive listener 흐름은 다음과 같다.

1. VMS가 UDP `3702` 포트에 WS-Discovery listener를 열어둔다.
2. 카메라가 네트워크에 들어오면 `Hello` 메시지를 multicast로 보낼 수 있다.
3. VMS는 `Hello`를 받아 장비 목록에 upsert한다.
4. 카메라가 정상적으로 네트워크에서 빠질 때 `Bye`를 보낼 수 있다.
5. VMS는 `Bye`를 받아 해당 장비를 offline으로 표시한다.

Resolve 흐름은 다음과 같다.

1. VMS가 특정 `EndpointReference`를 알고 있다.
2. VMS가 `Resolve` 메시지를 multicast로 보낸다.
3. 대상 장비가 `ResolveMatches`로 응답한다.
4. VMS는 응답에서 `XAddrs`를 갱신한다.

`XAddrs` 예시는 다음과 같다.

```text
http://192.168.0.10/onvif/device_service
```

이 URL은 이후 Device Service의 `GetDeviceInformation`, `GetCapabilities` 등을 호출할 때 사용한다.

## Discovery 구현 흐름

### 1. gSOAP context 생성

Discovery는 UDP multicast이므로 gSOAP context를 UDP 모드로 생성한다.

```cpp
soap* context = soap_new1(SOAP_IO_UDP);
```

그리고 namespace와 multicast 옵션을 설정한다.

```cpp
soap_set_namespaces(context, namespaces);
context->connect_flags = SO_BROADCAST;
context->ipv4_multicast_ttl = 1;
context->recv_timeout = 3;
context->send_timeout = 3;
context->connect_timeout = 3;
```

- `namespaces`: 생성된 namespace mapping table
- `SO_BROADCAST`: UDP broadcast/multicast 송신 허용
- `ipv4_multicast_ttl = 1`: 로컬 네트워크 범위로 제한

### 2. Probe 전송

핵심 호출은 `soap_wsdd_Probe`다.

```cpp
soap_wsdd_Probe(
    context,
    SOAP_WSDD_ADHOC,
    SOAP_WSDD_TO_TS,
    "soap.udp://239.255.255.250:3702",
    id,
    nullptr,
    "\"http://www.onvif.org/ver10/network/wsdl\":NetworkVideoTransmitter",
    nullptr,
    nullptr);
```

의미는 다음과 같다.

- `SOAP_WSDD_ADHOC`: multicast discovery 방식
- `SOAP_WSDD_TO_TS`: Target Service, 즉 장비를 찾음
- endpoint: WS-Discovery multicast 주소
- `id`: Probe 메시지의 고유 WS-Addressing MessageID
- Types: ONVIF Network Video Transmitter 장비만 찾겠다는 조건

타입 문자열은 prefix에 의존하지 않도록 namespace literal QName 형태를 사용한다.

```text
"http://www.onvif.org/ver10/network/wsdl":NetworkVideoTransmitter
```

### 3. ProbeMatches 수신

Probe를 보낸 뒤 같은 UDP context로 잠깐 응답을 기다린다.

```cpp
soap_wsdd_listen(context, listenTimeoutMicros(options.listenTimeout));
```

현재 기본 timeout은 3초다. 이 시간 동안 카메라들이 보내는 `ProbeMatches` 응답을 받는다.

### 4. Passive listener 실행

`start()`는 주기 Probe timer와 함께 passive listener thread를 시작한다. listener는 기본 UDP `3702` 포트에 bind하고 짧은 timeout으로 `soap_wsdd_listen`을 반복 호출한다.

```cpp
soap_bind(context, nullptr, options.passiveListenPort, 100);
soap_wsdd_listen(context, listenTimeoutMicros(options.passiveListenPollTimeout));
```

현재 기본 poll timeout은 500ms다. `stop()`이 호출되면 atomic flag를 내리고, 최대 poll timeout 정도 기다린 뒤 listener thread를 join한다.

### 5. Resolve 요청

특정 EndpointReference의 transport address를 다시 확인해야 하면 `resolveOnce(endpointReference)`를 호출한다.

```cpp
soap_wsdd_Resolve(
    context,
    SOAP_WSDD_ADHOC,
    SOAP_WSDD_TO_TS,
    "soap.udp://239.255.255.250:3702",
    id,
    nullptr,
    endpointReference.c_str());
```

응답은 `ResolveMatches` event handler로 들어오고, 내부 장비 목록에도 upsert된다.

### 6. gSOAP event handler에서 응답 처리

gSOAP WS-Discovery plugin은 응답을 받으면 정해진 이름의 callback 함수를 호출한다.

```cpp
void wsdd_event_ProbeMatches(
    soap* context,
    unsigned int InstanceId,
    const char* SequenceId,
    unsigned int MessageNumber,
    const char* MessageID,
    const char* RelatesTo,
    wsdd__ProbeMatchesType* matches);
```

이 함수 이름과 signature는 gSOAP plugin이 요구하는 것이다. 임의로 바꾸면 안 된다.

현재 구현에서는 다음 event handler들을 사용한다.

- `wsdd_event_Hello`: passive listener에서 장비 online/upsert 처리
- `wsdd_event_Bye`: passive listener에서 장비 offline 처리
- `wsdd_event_ProbeMatches`: Probe 응답을 장비 목록으로 변환
- `wsdd_event_ResolveMatches`: Resolve 응답을 장비 목록으로 변환

`wsdd_event_Probe`와 `wsdd_event_Resolve`는 VMS가 Target Service 역할을 하지 않으므로 현재는 ad-hoc mode만 반환한다.

### 7. gSOAP struct에서 내부 모델로 변환

응답 하나는 `wsdd__ProbeMatchType`로 들어온다. 주요 field는 다음과 같다.

```cpp
match.wsa5__EndpointReference.Address
match.Types
match.Scopes->__item
match.XAddrs
match.MetadataVersion
```

이를 내부 모델로 변환한다.

```cpp
struct OnvifDiscoveredDevice {
    std::string endpointReference;
    std::string types;
    std::string scopes;
    std::vector<std::string> xaddrs;
    std::uint32_t metadataVersion = 0;
    bool online = true;
};
```

`XAddrs`는 공백으로 여러 URL이 올 수 있으므로 whitespace 기준으로 분리한다.

## 현재 Discovery 서비스 API

파일: `lib/app-onvif/include/OnvifDiscoveryService.h`

주요 API는 다음과 같다.

```cpp
class OnvifDiscoveryService {
public:
    void start();
    void stop();

    std::vector<OnvifDiscoveredDevice> discoverOnce();
    std::optional<OnvifDiscoveredDevice> resolveOnce(const std::string& endpointReference);
    std::vector<OnvifDiscoveredDevice> devices() const;
};
```

- `discoverOnce()`: 즉시 1회 Probe 기반 Discovery 수행
- `resolveOnce()`: 특정 EndpointReference에 대해 Resolve 수행
- `start()`: `IntervalTimer` 기반 주기 Probe와 passive listener 시작
- `stop()`: 주기 Probe와 passive listener 중지
- `devices()`: 마지막으로 수집한 장비 상태 반환

`main.cpp`에서는 설정값 `app.onvif.discovery.intervalMs`를 이용해 주기 실행한다.

## Device Service: GetDeviceInformation

ONVIF Device Service는 HTTP 기반 SOAP API다. Discovery에서 얻은 `XAddrs` URL을 endpoint로 사용한다.

```cpp
OnvifDeviceClient client;
std::optional<OnvifDeviceInformation> info =
    client.getDeviceInformation("http://192.168.0.10/onvif/device_service");
```

`OnvifDeviceClient`는 내부에서 gSOAP 생성 함수인 `soap_call___tds__GetDeviceInformation`을 호출한다.

```cpp
_tds__GetDeviceInformation request;
_tds__GetDeviceInformationResponse response;

soap_call___tds__GetDeviceInformation(
    context.get(),
    deviceServiceUrl.c_str(),
    "http://www.onvif.org/ver10/device/wsdl/GetDeviceInformation",
    &request,
    response);
```

응답은 애플리케이션 DTO로 복사한다.

```cpp
struct OnvifDeviceInformation {
    std::string manufacturer;
    std::string model;
    std::string firmwareVersion;
    std::string serialNumber;
    std::string hardwareId;
};
```

현재 `OnvifDeviceClient`는 endpoint URL이 비어 있거나 SOAP fault/transport 오류가 발생하면 `std::nullopt`를 반환한다.

## Device Service: GetCapabilities

`GetCapabilities`는 이후 ONVIF 서비스 endpoint를 얻기 위한 호출이다. 현재는 전체 category를 요청하고, 응답에서 자주 쓰는 XAddr만 DTO로 복사한다.

```cpp
std::optional<OnvifDeviceCapabilities> capabilities =
    client.getCapabilities(deviceServiceUrl);

if (capabilities && !capabilities->mediaXAddr.empty()) {
    // Media Service endpoint로 GetProfiles/GetStreamUri에 사용한다.
}
```

```cpp
struct OnvifDeviceCapabilities {
    std::string analyticsXAddr;
    std::string deviceXAddr;
    std::string eventsXAddr;
    std::string imagingXAddr;
    std::string mediaXAddr;
    std::string ptzXAddr;
};
```

## Media Service: GetProfiles

`GetProfiles`는 `GetCapabilities`에서 얻은 `mediaXAddr`를 endpoint로 사용한다. 응답의 profile token은 다음 단계인 `GetStreamUri`의 `ProfileToken`으로 넘긴다.

```cpp
OnvifMediaClient mediaClient;
std::optional<std::vector<OnvifMediaProfile>> profiles =
    mediaClient.getProfiles(capabilities->mediaXAddr);
```

`OnvifMediaClient`는 내부에서 gSOAP 생성 함수인 `soap_call___trt__GetProfiles`를 호출한다.

```cpp
_trt__GetProfiles request;
_trt__GetProfilesResponse response;

soap_call___trt__GetProfiles(
    context.get(),
    mediaServiceUrl.c_str(),
    "http://www.onvif.org/ver10/media/wsdl/GetProfiles",
    &request,
    response);
```

응답은 애플리케이션 DTO로 복사한다.

```cpp
struct OnvifMediaProfile {
    std::string token;
    std::string name;
    bool fixed = false;
    std::string videoSourceConfigurationToken;
    std::string videoEncoderConfigurationToken;
    std::string audioSourceConfigurationToken;
    std::string audioEncoderConfigurationToken;
};
```

## Media Service: GetStreamUri

`GetStreamUri`는 `GetProfiles`에서 얻은 profile token을 실제 재생/수신 가능한 media URI로 변환한다. 현재 wrapper의 기본 요청은 라이브 RTSP 수신에 맞춰 `RTP-Unicast over RTSP`로 보낸다.

```cpp
std::optional<OnvifStreamUri> streamUri =
    mediaClient.getStreamUri(capabilities->mediaXAddr, profile.token);

if (streamUri) {
    // streamUri->uri를 app-media-server의 live ingest URL로 넘긴다.
}
```

`OnvifMediaClient`는 내부에서 gSOAP 생성 함수인 `soap_call___trt__GetStreamUri`를 호출한다.

```cpp
_trt__GetStreamUri request;
_trt__GetStreamUriResponse response;

request.StreamSetup = streamSetup;
request.ProfileToken = profileToken;

soap_call___trt__GetStreamUri(
    context.get(),
    mediaServiceUrl.c_str(),
    "http://www.onvif.org/ver10/media/wsdl/GetStreamUri",
    &request,
    response);
```

응답은 애플리케이션 DTO로 복사한다.

```cpp
struct OnvifStreamUri {
    std::string uri;
    bool invalidAfterConnect = false;
    bool invalidAfterReboot = false;
    std::string timeout;
};
```

WS-Security UsernameToken은 공용 `OnvifClientOptions`로 Device/Media/PTZ client에 동일하게 설정할 수 있다. 다만 HTTP Digest 인증은 아직 구현하지 않았다.

## ONVIF 구현 로드맵

일반적인 ONVIF client 구현 순서는 다음과 같다.

```text
Discovery
  -> XAddrs 획득
  -> Device.GetDeviceInformation
  -> Device.GetCapabilities
  -> Media.GetProfiles
  -> Media.GetStreamUri
  -> PTZ.GetConfigurations/GetConfigurationOptions
  -> PTZ Move/Stop
  -> Preset 조회/저장/이동
  -> Preset Tour 생성/수정/운영
  -> DB 저장/API 연결
```

이 순서로 가는 이유는 Discovery가 Device Service URL을 알려주고, Device Service의 `GetCapabilities`가 Media, Events, PTZ, Imaging 같은 다음 서비스 endpoint를 알려주기 때문이다. 즉 `GetCapabilities`는 이후 기능 확장을 위한 지도 역할을 한다.

### 1. Discovery 안정화

현재 구현된 상태다.

- active Probe로 장비 검색
- passive listener로 Hello/Bye 수신
- Resolve로 특정 EndpointReference의 XAddrs 재조회
- `OnvifDiscoveredDevice.xaddrs`에 Device Service endpoint 후보 저장

확인할 것:

- Linux host 또는 Linux Docker `--network host` 환경에서 실제 장비 Discover 확인
- Windows/WSL/Docker 환경에서는 multicast 제약 여부 확인
- `xaddrs`가 VMS에서 접근 가능한 IP/host를 담는지 확인

### 2. Device.GetDeviceInformation 연결

현재 client wrapper는 구현되어 있고, 애플리케이션 흐름에는 아직 연결하지 않았다.

해야 할 일:

- Discovery 결과의 `xaddrs`에서 Device Service URL 선택
- `OnvifDeviceClient::getDeviceInformation()` 호출
- manufacturer, model, firmwareVersion, serialNumber, hardwareId 확인
- 실패 시 SOAP fault와 transport 오류 로그 정리

주의할 점:

- `endpointReference`가 아니라 `xaddrs`를 Device Service URL로 사용한다.
- 인증이 필요한 장비는 이 단계에서 실패할 수 있다.
- 처음에는 임시 로그 확인으로 충분하고, DB 저장은 뒤 단계에서 묶는다.

### 3. Device.GetCapabilities 구현

현재 client wrapper는 구현되어 있고, 애플리케이션 흐름에는 아직 연결하지 않았다.

완료된 일:

- `OnvifDeviceClient::getCapabilities()` 추가
- Device, Media, Events, Imaging, PTZ XAddr를 담는 DTO 추가
- 전체 capability를 요청하도록 `tt__CapabilityCategory::All` 사용
- 응답에서 Media Service XAddr를 우선 추출

예상 DTO 형태:

```cpp
struct OnvifDeviceCapabilities {
    std::string analyticsXAddr;
    std::string deviceXAddr;
    std::string eventsXAddr;
    std::string imagingXAddr;
    std::string mediaXAddr;
    std::string ptzXAddr;
};
```

`GetCapabilities`를 먼저 구현하는 이유는 Media Service endpoint를 알아야 이후 `GetProfiles`, `GetStreamUri`로 진행할 수 있기 때문이다.

### 4. 인증 처리

WS-Security UsernameToken은 현재 구현되어 있다. `OnvifClientOptions`에 인증 정보를 넣으면 Device/Media SOAP 호출에 Timestamp와 UsernameToken이 붙는다.

```cpp
OnvifClientOptions options;
options.wsSecurity.enabled = true;
options.wsSecurity.username = "admin";
options.wsSecurity.password = "password";
options.wsSecurity.passwordType = OnvifWsSecurityPasswordType::Digest;
options.wsSecurity.timestampLifetime = std::chrono::seconds(300);

OnvifDeviceClient deviceClient(options);
OnvifMediaClient mediaClient(options);
```

완료된 일:

- `wsse.h`를 gSOAP 통합 생성 입력에 추가
- `wsseapi.c`, `smdevp.c`, `mecevp.c`, `struct_timeval.c` 빌드 연결
- `gsoapssl++`, OpenSSL 링크
- UsernameToken `PasswordDigest` 지원
- UsernameToken `PasswordText` 선택 지원
- `GetDeviceInformation`, `GetCapabilities` 호출에 WSSE 적용

아직 남은 일:

- HTTP Digest 인증 구현
- 실제 장비에서 Digest/Text 호환성 확인
- 인증 실패와 네트워크 실패를 더 명확히 구분하는 오류 모델 정리

주의할 점:

- ONVIF 장비마다 HTTP Digest를 요구하는 경우와 WS-Security UsernameToken을 요구하는 경우가 다를 수 있다.
- Discovery 자체는 보통 인증이 필요 없고, Device/Media 호출부터 인증이 필요해진다.
- `PasswordText`는 HTTPS 같은 보호된 전송과 함께 쓰는 편이 좋다.

### 5. Media.GetProfiles/GetStreamUri 구현

현재 client wrapper는 구현되어 있고, 애플리케이션 흐름에는 아직 연결하지 않았다.

완료된 일:

- ONVIF Media WSDL vendoring
- Device WSDL과 Media WSDL을 `onvif_services_wsdl.h`로 통합 생성
- `onvif_services.h`에 통합 생성 header 추가
- `OnvifMediaClient` 추가
- `OnvifMediaClient::getProfiles()` 구현
- `OnvifMediaClient::getStreamUri()` 구현
- profile token, name, 주요 configuration token DTO 매핑
- Media URI, invalid flag, timeout DTO 매핑

아직 남은 일:

- `GetProfiles`, `GetStreamUri` 결과를 DB/API 흐름에 연결
- 실제 장비에서 profile token, configuration token, RTSP URI 확인
- RTSP URI를 `app-media-server` live ingest로 넘기는 orchestration 구현

예상 흐름:

```text
Device.GetCapabilities
  -> mediaXAddr
  -> Media.GetProfiles
  -> profile token
  -> Media.GetStreamUri
  -> RTSP URL
```

### 6. 애플리케이션 흐름 연결

Discovery, Device, Media 호출이 각각 동작하면 이를 하나의 application service로 묶는다.

예상 구조:

```text
OnvifDiscoveryService
  -> OnvifDeviceClient
  -> OnvifMediaClient
  -> VMS DB 저장
  -> Admin API 노출
```

해야 할 일:

- 발견 장비 upsert 정책 결정
- serialNumber 또는 endpointReference 기반 중복 처리
- DeviceInformation 저장
- Capability 저장
- Media profile/channel 저장
- RTSP URL 저장 또는 필요 시 재조회 정책 결정

`main.cpp`에는 세부 ONVIF 호출을 직접 많이 넣지 않고, orchestration service를 생성하고 시작하는 wiring만 두는 편이 좋다.

## 개발 시 주의할 점

### 생성 코드와 직접 작성 코드 분리

직접 작성하는 코드는 `lib/app-onvif`에 둔다. gSOAP 생성 코드는 build directory에 생성하고 소스 트리에 직접 커밋하지 않는다.

### SOAP XML을 직접 만들지 않는다

요청 XML 문자열을 직접 작성하지 않는다. gSOAP가 생성한 함수와 struct를 사용한다.

### gSOAP event handler 이름 유지

`wsdd_event_ProbeMatches` 같은 callback 이름은 gSOAP plugin이 찾는 symbol이다. 이름이나 signature를 바꾸면 link 또는 runtime 동작이 깨질 수 있다.

### namespace table은 한 번만 정의

`*.nsmap` 파일은 전역 `namespaces[]`를 정의한다. 여러 `.cpp`에서 각각 include하면 중복 정의가 생길 수 있다. 현재는 Discovery 구현부에서 한 번 include하고, Device client는 `extern struct Namespace namespaces[];`로 공유한다.

### UDP socket 사용 방식

Discovery는 Probe를 보낸 UDP socket으로 응답이 돌아오는 경우가 많다. 그래서 현재 구현은 같은 gSOAP UDP context를 bind, send, listen에 사용한다.

### 인증은 Discovery 이후 문제

Discovery 자체는 보통 인증 없이 가능하다. Device/Media 호출부터는 카메라에 따라 HTTP Digest 또는 WS-Security UsernameToken이 필요할 수 있다.

완료된 것:

- `app-onvif` 독립 모듈 추가
- WS-Discovery용 gSOAP 코드 빌드 중 생성
- ONVIF Device Management WSDL/XSD vendoring
- Discovery와 Device Service 통합 gSOAP 코드 생성
- UDP multicast Probe 전송
- ProbeMatches 응답 수집
- UDP 3702 passive listener 실행
- Hello 수신 시 장비 online/upsert 처리
- Bye 수신 시 장비 offline 처리
- Resolve/ResolveMatches 지원
- 발견 장비를 `OnvifDiscoveredDevice`로 변환
- `OnvifDeviceClient`로 `GetDeviceInformation` 호출 구현
- `OnvifDeviceClient`로 `GetCapabilities` 호출 구현
- ONVIF Media WSDL vendoring
- ONVIF PTZ WSDL vendoring
- Device/Media/PTZ WSDL 통합 gSOAP 생성
- `OnvifMediaClient`로 `GetProfiles` 호출 구현
- `OnvifMediaClient`로 `GetStreamUri` 호출 구현
- `OnvifPtzClient`로 `GetNodes`, `GetConfigurations`, `GetConfigurationOptions` 호출 구현
- `OnvifPtzClient`로 `GetPresets`, `SetPreset`, `GotoPreset`, `RemovePreset` 호출 구현
- `OnvifPtzClient`로 `ContinuousMove`, `Stop` 호출 구현
- VMS PTZ 이동/정지 API를 DB channel/profile/PTZ target 조회와 `OnvifPtzClient` 호출 흐름에 연결
- VMS 프리셋 API를 Controller-Service-Repository 구조로 분리
- `ptz_preset` 기반 프리셋 목록/저장/이동/수정/삭제 1차 구현
- WS-Security UsernameToken 인증 옵션 구현
- `app-security` 공용 `SecretCodec`로 `plain:<secret>`와 기존 raw 저장값 처리
- `main.cpp`에서 주기 Discovery와 passive listener 시작

- `SecretCodec`의 키 기반 암호화 포맷/키 관리 정책 정리
- 장비 `GetPresets` 결과와 VMS `ptz_preset` cache 동기화 정책 정리
- 실제 PTZ 카메라 상호 운용 테스트
- 프리셋 투어 구현
- Preset Tour 생성/수정/운영 구현
- HTTP Digest 인증 처리
