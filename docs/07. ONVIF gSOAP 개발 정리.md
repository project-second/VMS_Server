# ONVIF gSOAP 개발 정리

이 문서는 VMS 서버에서 ONVIF 기능을 직접 XML 하드코딩으로 구현하지 않고, gSOAP 코드 생성과 gSOAP plugin을 이용해 개발하는 흐름을 정리한다.

현재 구현된 범위는 ONVIF Discovery이며, Device/Media/Event 서비스는 이후 ONVIF WSDL을 추가한 뒤 같은 방식으로 확장한다.

## 현재 구조

```text
lib/app-onvif/
  CMakeLists.txt
  OnvifDiscoveryService.cpp
  onvif_wsdd.h
  include/
    OnvifDiscoveryService.h

third_party/onvif/
  CMakeLists.txt
  README.md
  wsdl/
  generated/
```

역할은 다음과 같다.

- `lib/app-onvif`: ONVIF 애플리케이션 모듈. Discovery, Device, Media 등 ONVIF 프로토콜 처리를 담당한다.
- `third_party/onvif/wsdl`: ONVIF Device/Media/Event 등 WSDL/XSD 입력 파일을 둘 위치다.
- `third_party/onvif/generated`: ONVIF WSDL에서 생성한 gSOAP 산출물을 둘 위치다.

현재 Discovery는 `lib/app-onvif` 안에서 빌드 시점에 최소 gSOAP 코드를 생성한다. 반면 Device/Media/Event용 전체 ONVIF gSOAP 코드는 아직 생성하지 않았다.

## gSOAP를 쓰는 이유

ONVIF는 SOAP 기반 프로토콜이다. SOAP 요청은 단순 JSON이나 REST 호출이 아니라 XML Envelope, Header, Body, namespace, WS-Addressing, WS-Security 같은 규칙을 따른다.

이를 문자열로 직접 만들면 다음 문제가 생긴다.

- XML namespace를 정확히 맞추기 어렵다.
- SOAP Header/Body 구조가 서비스마다 복잡하다.
- 응답 XML parsing 코드가 지저분해진다.
- ONVIF 스펙 변경이나 서비스 확장 시 유지보수가 어렵다.

그래서 gSOAP를 사용한다. gSOAP는 WSDL/XSD 또는 gSOAP import header를 입력으로 받아 C/C++ 타입과 SOAP 호출 함수를 생성한다.

즉 직접 하지 않는 일은 다음과 같다.

- SOAP XML 문자열 생성
- XML namespace 처리
- SOAP Envelope/Header/Body 직렬화
- SOAP 응답 XML 파싱
- WS-Addressing Header 처리

대신 우리가 작성하는 코드는 생성된 C/C++ 함수와 struct를 사용하는 형태가 된다.

## gSOAP 도구

주요 도구는 두 가지다.

```bash
wsdl2h
soapcpp2
```

### wsdl2h

WSDL/XSD를 읽어서 gSOAP용 C/C++ header를 만든다.

예상 흐름:

```bash
wsdl2h -c++17 -x \
  -o third_party/onvif/generated/onvif.h \
  -I third_party/onvif/wsdl \
  -I /usr/share/gsoap/import \
  -t /usr/share/gsoap/WS/typemap.dat \
  third_party/onvif/wsdl/*.wsdl third_party/onvif/wsdl/*.xsd
```

### soapcpp2

`wsdl2h`가 만든 header 또는 직접 작성한 gSOAP input header를 읽어서 실제 C/C++ 코드를 생성한다.

예상 흐름:

```bash
soapcpp2 -c++17 -C -x -w \
  -d third_party/onvif/generated \
  -I /usr/share/gsoap/import:third_party/onvif/generated \
  third_party/onvif/generated/onvif.h
```

주요 옵션 의미:

- `-c++17`: C++17 코드 생성
- `-C`: client-side 코드만 생성
- `-x`: sample XML 생성 생략
- `-w`: WSDL/schema 출력 생략
- `-d`: 생성 산출물 디렉터리 지정
- `-I`: gSOAP import header 검색 경로

## 생성 산출물

`soapcpp2`는 보통 다음 파일들을 만든다.

```text
soapH.h
soapStub.h
soapC.cpp
soapClient.cpp
*.nsmap
```

각 파일의 역할은 다음과 같다.

- `soapH.h`: 생성 타입과 함수 선언을 모은 header
- `soapStub.h`: gSOAP가 생성한 struct/type 정의
- `soapC.cpp`: SOAP 직렬화/역직렬화 코드
- `soapClient.cpp`: SOAP client 호출 stub
- `*.nsmap`: XML namespace mapping table

Discovery 구현에서는 이 파일들이 `build/lib/app-onvif/generated` 아래에 빌드 중 생성된다.

## ONVIF Discovery 원리

ONVIF Discovery는 일반 HTTP API가 아니라 WS-Discovery라는 SOAP 기반 UDP multicast 프로토콜이다.

흐름은 다음과 같다.

1. VMS가 UDP multicast 주소 `239.255.255.250:3702`로 `Probe` 메시지를 보낸다.
2. 같은 네트워크의 ONVIF 카메라들이 Probe를 받는다.
3. 카메라가 `ProbeMatches` 메시지로 응답한다.
4. 응답 안에 `EndpointReference`, `Types`, `Scopes`, `XAddrs`가 들어 있다.
5. VMS는 `XAddrs`에서 카메라의 ONVIF Device Service URL을 얻는다.

`XAddrs` 예시는 다음과 같다.

```text
http://192.168.0.10/onvif/device_service
```

이 URL은 이후 Device Service의 `GetDeviceInformation`, `GetCapabilities` 등을 호출할 때 사용한다.

## Discovery 구현 흐름

### 1. Discovery용 gSOAP 입력 header 작성

파일: `lib/app-onvif/onvif_wsdd.h`

```cpp
#import "wsdd.h"
```

`wsdd.h`는 gSOAP가 제공하는 WS-Discovery 스키마 import header다. 보통 다음 경로에 있다.

```text
/usr/share/gsoap/import/wsdd.h
```

Discovery는 표준 WS-Discovery 프로토콜을 사용하므로, ONVIF 전체 WSDL 없이도 `wsdd.h`만으로 먼저 구현할 수 있다.

### 2. CMake에서 soapcpp2 실행

파일: `lib/app-onvif/CMakeLists.txt`

빌드 시 다음과 같은 `soapcpp2` 명령을 실행한다.

```bash
soapcpp2 -c++17 -C -x -w \
  -d build/lib/app-onvif/generated \
  -I /usr/share/gsoap/import \
  lib/app-onvif/onvif_wsdd.h
```

이 결과 `soapH.h`, `soapStub.h`, `soapC.cpp`, `soapClient.cpp`, `wsdd.nsmap` 등이 생성된다.

### 3. WS-Discovery plugin 빌드

Discovery는 생성 코드 외에도 gSOAP plugin이 필요하다.

```cmake
/usr/share/gsoap/plugin/wsddapi.c
/usr/share/gsoap/plugin/wsaapi.c
```

역할은 다음과 같다.

- `wsddapi.c`: WS-Discovery helper API 제공
- `wsaapi.c`: WS-Addressing 처리

이 파일들은 생성된 C++ header를 include하므로 C++로 컴파일하도록 CMake에서 `LANGUAGE CXX`를 지정한다.

또한 gSOAP runtime인 `gsoap++`에 링크한다.

```cmake
target_link_libraries(app-onvif PUBLIC app-util gsoap++)
```

### 4. gSOAP context 생성

Discovery는 UDP multicast이므로 gSOAP context를 UDP 모드로 생성한다.

```cpp
soap* context = soap_new1(SOAP_IO_UDP);
```

그리고 namespace와 multicast 옵션을 설정한다.

```cpp
soap_set_namespaces(context, namespaces);
context->connect_flags = SO_BROADCAST;
context->ipv4_multicast_ttl = 1;
context->recv_timeout = 3;
context->send_timeout = 3;
context->connect_timeout = 3;
```

- `namespaces`: 생성된 `wsdd.nsmap`의 namespace table
- `SO_BROADCAST`: UDP broadcast/multicast 송신 허용
- `ipv4_multicast_ttl = 1`: 로컬 네트워크 범위로 제한

### 5. Probe 전송

핵심 호출은 `soap_wsdd_Probe`다.

```cpp
soap_wsdd_Probe(
    context,
    SOAP_WSDD_ADHOC,
    SOAP_WSDD_TO_TS,
    "soap.udp://239.255.255.250:3702",
    id,
    nullptr,
    "\"http://www.onvif.org/ver10/network/wsdl\":NetworkVideoTransmitter",
    nullptr,
    nullptr);
```

의미는 다음과 같다.

- `SOAP_WSDD_ADHOC`: multicast discovery 방식
- `SOAP_WSDD_TO_TS`: Target Service, 즉 장비를 찾음
- endpoint: WS-Discovery multicast 주소
- `id`: Probe 메시지의 고유 WS-Addressing MessageID
- Types: ONVIF Network Video Transmitter 장비만 찾겠다는 조건

타입 문자열은 prefix에 의존하지 않도록 namespace literal QName 형태를 사용한다.

```text
"http://www.onvif.org/ver10/network/wsdl":NetworkVideoTransmitter
```

### 6. ProbeMatches 수신

Probe를 보낸 뒤 같은 UDP context로 잠깐 응답을 기다린다.

```cpp
soap_wsdd_listen(context, listenTimeoutMicros(options.listenTimeout));
```

현재 기본 timeout은 3초다. 이 시간 동안 카메라들이 보내는 `ProbeMatches` 응답을 받는다.

### 7. gSOAP event handler에서 응답 처리

gSOAP WS-Discovery plugin은 응답을 받으면 정해진 이름의 callback 함수를 호출한다.

```cpp
void wsdd_event_ProbeMatches(
    soap* context,
    unsigned int InstanceId,
    const char* SequenceId,
    unsigned int MessageNumber,
    const char* MessageID,
    const char* RelatesTo,
    wsdd__ProbeMatchesType* matches);
```

이 함수 이름과 signature는 gSOAP plugin이 요구하는 것이다. 임의로 바꾸면 안 된다.

현재 구현에서는 이 callback 안에서 `collectProbeMatches`를 호출해 gSOAP struct를 내부 모델로 변환한다.

### 8. gSOAP struct에서 내부 모델로 변환

응답 하나는 `wsdd__ProbeMatchType`로 들어온다. 주요 field는 다음과 같다.

```cpp
match.wsa5__EndpointReference.Address
match.Types
match.Scopes->__item
match.XAddrs
match.MetadataVersion
```

이를 내부 모델로 변환한다.

```cpp
struct OnvifDiscoveredDevice {
    std::string endpointReference;
    std::string types;
    std::string scopes;
    std::vector<std::string> xaddrs;
    std::uint32_t metadataVersion = 0;
};
```

`XAddrs`는 공백으로 여러 URL이 올 수 있으므로 whitespace 기준으로 분리한다.

## 현재 Discovery 서비스 API

파일: `lib/app-onvif/include/OnvifDiscoveryService.h`

주요 API는 다음과 같다.

```cpp
class OnvifDiscoveryService {
public:
    void start();
    void stop();

    std::vector<OnvifDiscoveredDevice> discoverOnce();
    std::vector<OnvifDiscoveredDevice> devices() const;
};
```

- `discoverOnce()`: 즉시 1회 Discovery 수행
- `start()`: `IntervalTimer`를 이용해 주기적으로 Discovery 수행
- `devices()`: 마지막 Discovery 결과 반환

`main.cpp`에서는 설정값 `app.onvif.discovery.intervalMs`를 이용해 주기 실행한다.

## Device/Media/Event 확장 방향

Discovery 다음 단계는 ONVIF Device Service다.

일반적인 순서는 다음과 같다.

1. `third_party/onvif/wsdl`에 ONVIF WSDL/XSD를 추가한다.
2. `cmake --build build --target onvif-gsoap-generate`를 실행한다.
3. `third_party/onvif/generated`에 생성된 코드를 확인한다.
4. `app-onvif`에서 생성된 client stub을 사용해 Device Service를 호출한다.
5. Discovery로 얻은 `XAddrs`를 Device Service endpoint로 사용한다.
6. `GetDeviceInformation`, `GetCapabilities`, `GetProfiles`, `GetStreamUri` 순서로 기능을 확장한다.

예상 호출 흐름은 다음과 같다.

```text
Discovery
  -> XAddrs 획득
  -> Device.GetDeviceInformation
  -> Device.GetCapabilities
  -> Media.GetProfiles
  -> Media.GetStreamUri
```

## 개발 시 주의할 점

### 생성 코드와 직접 작성 코드 분리

직접 작성하는 코드는 `lib/app-onvif`에 둔다. ONVIF WSDL에서 생성한 큰 코드들은 `third_party/onvif/generated`에 둔다.

Discovery 전용 최소 생성 코드는 현재 build directory에 생성한다.

### SOAP XML을 직접 만들지 않는다

요청 XML 문자열을 직접 작성하지 않는다. gSOAP가 생성한 함수와 struct를 사용한다.

### gSOAP event handler 이름 유지

`wsdd_event_ProbeMatches` 같은 callback 이름은 gSOAP plugin이 찾는 symbol이다. 이름이나 signature를 바꾸면 link 또는 runtime 동작이 깨질 수 있다.

### UDP socket 사용 방식

Discovery는 Probe를 보낸 UDP socket으로 응답이 돌아오는 경우가 많다. 그래서 현재 구현은 같은 gSOAP UDP context를 bind, send, listen에 사용한다.

### 인증은 Discovery 이후 문제

Discovery 자체는 보통 인증 없이 가능하다. Device/Media 호출부터는 카메라에 따라 HTTP Digest 또는 WS-Security UsernameToken이 필요할 수 있다.

## 현재 상태 요약

완료된 것:

- `app-onvif` 독립 모듈 추가
- WS-Discovery용 gSOAP 코드 빌드 중 생성
- UDP multicast Probe 전송
- ProbeMatches 응답 수집
- 발견 장비를 `OnvifDiscoveredDevice`로 변환
- `main.cpp`에서 주기 Discovery 시작

아직 하지 않은 것:

- ONVIF Device/Media/Event WSDL vendoring
- Device/Media/Event용 gSOAP 코드 생성
- Discovery 결과 DB 저장
- Device Service `GetDeviceInformation` 호출
- Media Service `GetProfiles`, `GetStreamUri` 호출
- 인증 처리
