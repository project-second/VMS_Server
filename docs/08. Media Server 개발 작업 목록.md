# Media Server 개발 작업 목록

이 문서는 VMS 서버의 실시간 다중 스트리밍, 녹화, 저장 영상 조회·재생·다운로드 목표와 현재 구현 상태를 정리한다.

## 현재 진행 상황

기준일: **2026-10-20**. 아래 상태는 현재 소스·설정·migration을 대조한 결과다. 이번 문서 갱신에서는 빌드, 패키징, 서버·DB 실행, 실제 카메라 및 player 테스트를 수행하지 않았다. 과거 문서의 빌드·패키징 통과 기록은 이번 검증 결과로 사용하지 않는다.

> 기능 표기: `[x]` 소스 구현 확인, `[~]` 부분 구현·추가 정책 필요, `[ ]` 미구현. `[x]`는 실제 장비·배포 환경의 동작 보장을 뜻하지 않는다. 테스트 목록의 `[ ]`는 검증이 남아 있음을 뜻한다.

현재 `lib/app-media-server`는 **H.264 RTSP 다중 수신 → MP4 segment 녹화 → encoded H.264 공유 RTSP relay**와 **저장 MP4 기반 HLS VOD** 구현을 포함한다. `VmsApplication`에 segment metadata DB 저장과 playback HTTP API도 연결되어 있다.

| 영역 | 현재 구현 | 남은 범위 |
| --- | --- | --- |
| 수신·녹화 | profile별 worker·pipeline, H.264 MP4 분할 저장, 오류/EOS 후 고정 3초 재연결 | 실제 카메라 검증, 인증·transport·timeout 옵션, 상태 API, H.265/audio |
| Live relay | 동일 profile의 ingest에서 encoded H.264 전달, 같은 mount의 RTSP client가 media 공유 | 사용자별 live session, viewer 수·idle 정책, RTSP 인증·권한 |
| Segment metadata | 메모리 변경 callback → `archive_segment` DB 저장, 시작 시 stale 상태 보정 | DB 실패 복구·파일 reconcile, 손상·누락 검사, 정확한 미디어 시각 |
| 목록·timeline | DB 페이지 목록·상세, 서울 날짜별 연속 구간 병합 | 명시적 gap·bucket, thumbnail, 요청 상태 필터, profile 선택 |
| 범위 재생 | 최대 1시간 HLS VOD 생성, TS HTTP 제공, 세션 token·15분 idle TTL | 비동기 변환, cache 상한·복구·정리, 세부 권한, player 검증 |
| 다운로드·운영 | 목표·설계 단계 | 개별/구간 다운로드, retention, 용량 관리, metric·health API |

현재 ingest/relay 구성:

```text
Camera RTSP (profile별 upstream)
  -> rtspsrc -> rtph264depay -> h264parse -> tee
       -> queue -> splitmuxsink -> MP4 segment
       -> bounded/leaky queue -> encoded H.264 appsink
            -> H264RelayHub
            -> RTSP media의 appsrc -> queue -> h264parse -> rtph264pay
                 -> 같은 mount를 공유하는 RTSP client N개
```

녹화와 relay의 `GstPipeline` 객체는 분리되어 있지만 upstream 연결과 encoded H.264 buffer를 공유한다. relay를 위해 별도 카메라 RTSP 연결을 만들거나 decode/re-encode하지 않는다. relay가 비활성화되면 ingest의 relay branch도 만들지 않는다.

현재 저장 영상 경로:

```text
RecordingSegmentStore 변경 callback
  -> VmsPlaybackService -> VmsPlaybackRepository -> archive_segment

Playback HTTP 요청
  -> deviceId/channelId로 DB profile 선택
  -> DB segment 조회 -> PlaybackSession -> HlsVodSession
  -> MP4를 TS로 순차 변환 -> playlist 생성·URL token 삽입
  -> session registry -> TS HTTP 제공
```

## 목표 기능 및 전체 구성

목표는 RTP/RTSP 다중 수신·중계, segment 파일·metadata 관리, 목록·timeline 조회, 범위 재생·seek, 개별/구간 다운로드, 보존 기간·용량 관리와 영상 접근 권한이다.

```text
ONVIF Discovery / Media -> GetProfiles / GetStreamUri
  -> MediaService / CameraManager -> CameraWorker / CameraPipeline
       -> Recorder / RecordingSegmentStore -> archive_segment
       -> H264RelayHub / RtspRelayServer -> RTSP viewer
  -> VmsPlaybackService / HLS VOD -> HTTP API / Player
```

별도의 `MediaStreamSource` registry, 사용자별 live session manager, download job service, retention worker는 후속 작업이다.

## ONVIF와 Live Stream 연결

`mediaXAddr`는 ONVIF Media Service endpoint다. `GetProfiles`, `GetStreamUri`로 얻은 RTSP URL을 ingest에 등록한다.

```text
OnvifDeviceProvisioningService::provisioningLoop()
  -> MediaService::addCamera(results)
  -> repository.ensureChannel() / upsertProfiles()
  -> channelId + profileToken으로 DB profile_id 조회
  -> camera_id = <device-name-slug>__ch<channel_id>__<profile-token>
  -> RtspRelayServer::add_h264_camera(config)
  -> CameraManager::add_camera(config)
       -> manager가 실행 중이면 worker 즉시 시작
  -> channels.service_rtsp_url 갱신
```

- `profiles.cctv_rtsp_url`에는 ONVIF 원본 URL을 저장한다.
- relay mount는 `/live/<camera_id>`이고 URL은 `rtsp://<advertisedHost>:<port>/live/<camera_id>`다.
- `channels.service_rtsp_url`은 해당 provisioning 결과에서 처음 등록되는 relay URL을 사용한다. playback의 `channels.use_profile` 우선 선택과 동일한 정책으로 통합되어 있지 않다.
- RTSP URI가 있는 ONVIF profile을 모두 ingest·녹화한다. 장비 1대에 profile이 여러 개면 profile별 upstream이 생긴다.
- 중복 camera ID 등록은 방지하지만 이미 등록된 worker의 URI·설정을 변경하는 경로는 없다.

현재 설정 예시:

```yaml
app:
  media:
    recording:
      rootDir: "recordings/onvif"
      splitSeconds: 5
    rtspRelay:
      enabled: true
      bindAddress: "0.0.0.0"
      port: 8555
      advertisedHost: "127.0.0.1"
```

`advertisedHost`는 클라이언트에서 접근 가능한 VMS 주소로 설정한다. 상대 녹화 경로는 프로세스 작업 디렉터리 기준이다. 재시작 후에도 DB의 파일 경로를 읽을 수 있도록 작업 디렉터리를 유지하거나 절대 경로를 사용한다. worker는 재연결 시도마다 파일명 접두사를 붙인다.

```text
<recordRootDir>/<camera_id>/<attempt_epoch_ms>_<retry_count>_%05d.mp4
```

현재 등록된 profile은 항상 ingest·녹화한다. `recordingEnabled`/`alwaysOn`/`lazyStart` 옵션과 viewer idle timeout에 따른 ingest 정지는 미구현이다.

## 7. 저장 영상 목록 조회: Segment 단위

```text
GET /devices/{deviceId}/playback/segments?channelId=1&page=1&size=10
```

- [x] device/channel 관계로 profile 조회: `channels.use_profile` 우선, 선택 불가 시 첫 enabled profile fallback
- [x] `completed`/`interrupted`이며 종료 시각이 있는 DB segment 조회
- [x] 최신 시작 시각 순 pagination: `page >= 1`, `size = 1..100`
- [x] numeric `segmentId`, 시작·종료·duration·file size·상태 응답
- [~] event type은 `CONTINUOUS` 고정, thumbnail·segment playback URL은 `null`
- [ ] 목록 `from`/`to`·status/event 필터, 명시적 profile 선택 API

시간 범위 겹침 DB 조회는 timeline·HLS 생성에 사용한다. 목록 API 자체는 시간 범위를 받지 않는다. enabled channel/profile 확인은 사용자별 영상 접근 권한 검증과 별개다.

## 8. 저장 영상 목록 조회: Timeline 단위

```text
GET /devices/{deviceId}/playback/timeline?channelId=1&date=2026-10-20
```

- [x] 서울 날짜 자정부터 24시간과 겹치는 DB segment 조회
- [x] 다음 segment 시작이 현재 종료 후 1.5초 이내면 연속 range로 병합
- [x] range 시작·종료·segment 수·범위 재생 URL 응답
- [x] timezone은 `Asia/Seoul`, 시간 표기는 `+09:00`
- [~] 분리된 range로 gap 간접 표현, 명시적 gap 목록 없음
- [ ] bucket·zoom·pagination/cache, 날짜 경계로 range를 자르는 정책
- [ ] 1시간 초과 timeline range를 playback 제한에 맞게 분할

현재 하루와 겹치는 원본 segment 시각으로 range를 만든다. 병합 range가 1시간을 넘으면 생성된 playback URL도 1시간 제한에 걸린다.

## 9. 영상 범위 재생

```text
GET /devices/{deviceId}/playback/stream?channelId=1&from=...&to=...
GET /playback/sessions/{sessionId}/segments/{fileName}?token=...
```

- [x] ISO-8601 `Z`/offset 포함 시각 파싱, `from < to`·최대 1시간 검증
- [x] DB closed segment 조회, 요청 overlap으로 MP4 offset·duration 계산
- [x] `PlaybackSession`·`HlsVodSession` cache 및 TS 계획 생성
- [x] 모든 TS 순차 변환 후 HLS VOD playlist 응답
- [x] `EXT-X-PROGRAM-DATE-TIME`·`EXTINF`·`EXT-X-ENDLIST` 생성
- [x] HTTP playlist의 TS URL을 session token 포함 endpoint로 변경
- [x] `VmsApplication`에 repository·service·controller 연결
- [~] session TTL·cache 정리: 아래 현재 구현·한계 참고
- [ ] 사용자·장치·채널별 재생 권한
- [ ] 비동기/lazy 변환·전용 worker·취소·변환 시간 제한

현재 cache·권한 동작:

- cache root는 녹화 root 부모 아래 `playback-cache`이며 별도 설정 키는 없다.
- mutex로 보호하는 process-local registry에 HLS session·token·마지막 접근 시각을 저장한다.
- token은 OpenSSL로 생성한 32바이트 난수의 64자리 hex다. 서명 URL·사용자별 token은 아니다.
- 유효한 TS 요청마다 idle TTL 15분을 갱신한다. 성공한 HLS 생성 및 TS 요청 시 만료 session·directory를 정리하며 상시 worker는 없다.
- playlist·목록·상세·timeline은 공통 Bearer 인증을 거친다. TS endpoint는 공통 Bearer 인증 예외이며 session token을 검증한다.
- token으로 해당 session의 등록 파일명만 허용한다. 사용자 ID·장치 권한·session 소유권 연결과 매 TS 요청의 사용자 상태 재확인은 없다.

남은 한계:

- [ ] session 수·cache 용량·동시 변환 수 상한
- [ ] 같은 범위 cache 재사용·중복 변환 방지
- [ ] 재시작 orphan cache·변환 실패 directory 정리
- [ ] cache 삭제 실패 재시도·파일 전송 중 삭제 경합 검증
- [ ] 실제 TS duration 측정 및 `EXTINF` 일치
- [ ] MP4 경계·녹화 gap의 `EXT-X-DISCONTINUITY` 정책
- [ ] interrupted/unfinalized MP4 검사·재생 불가 파일 제외
- [ ] TS 전체를 `std::string`으로 읽는 방식의 파일·비동기 전송 개선

변환은 HTTP 요청 처리 중 수행되며 EOS/ERROR 대기에 전체 시간 제한이 없다. registry는 재시작 시 소실되어 기존 token URL을 복구하지 않는다. 녹화 공백은 재생 entry에서 빠지므로 player의 누적 재생 시간과 CCTV 절대 시각이 달라질 수 있다.

## 10. 재생 중 Seek 지원

- [x] 내부 `PlaybackService::seek()`의 절대 시각 → entry·파일 offset 계산
- [x] 범위 밖·녹화 공백 감지, 절대 timeline offset과 실제 재생 offset 구분
- [x] TS 변환 시 segment 시작 offset·종료 범위 적용
- [~] offset 0은 key-unit seek/remux, 양수는 accurate seek와 decode/re-encode로 정확 절단 시도
- [ ] keyframe index·실제 seek 오차·첫 frame 검증
- [ ] server-side 절대 시각 seek HTTP endpoint·gap의 nearest range 정책
- [ ] 목표 player `currentTime` seek·segment 경계 연속 재생 검증

중간 시작 절단은 `avdec_h264 -> videoconvert -> x264enc`를 사용한다. 정확 seek를 요청하는 코드가 있다는 의미이며 실제 frame 정확도는 미검증이다. `x264enc` plugin과 의존 library는 CPack 수집 목록에 포함하며, 빌드 환경에 `gstreamer1.0-plugins-ugly`가 설치되어 있어야 한다.

## 11. 구간 다운로드

이전 문서의 검증 기록은 다음과 같다. 원기록의 실행 날짜·명령·산출물을 이번 갱신에서 재확인하지 않았으므로 현재 소스 전체의 검증 완료로 사용하지 않는다.

- 새 `CameraManager` 기반 전체 빌드와 TGZ 패키징 통과 기록

## 21. 후속 구현·검증 우선순위

1. package-only element 확인. 특히 중간 시작 HLS의 `x264enc` 로드와 변환을 검증한다.
2. DB migration 적용 후 실제 카메라 ingest → 녹화·공유 relay → DB 저장 → 재시작 조회 → HLS 재생을 검증한다.
3. callback 시각·파일 duration, exact trim·`EXTINF`·discontinuity, 1시간 초과 timeline URL을 다룬다.
4. 사용자·장치·채널 권한과 HLS session 소유권·접근 회수 정책을 연결한다.
5. 변환 시간·동시 실행 제한·비동기 처리와 cache 용량·실패·재시작 정리를 추가한다.
6. DB 실패 복구·파일 reconcile·손상 검사, 녹화 profile 선택·설정 갱신을 구현한다.
7. 개별 segment 재생·다운로드 및 구간 export job을 구현한다.
8. retention·용량 정책·metric·health API를 추가하고 장시간·다중 stream 부하를 검증한다.

이미 구현된 DB 영속화와 playback API는 실행 검증 및 남은 정책을 완료 기준으로 삼는다.
